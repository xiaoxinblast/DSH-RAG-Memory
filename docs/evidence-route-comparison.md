# v7／原文片段／原文加轻量索引：隔离离线对照

**结论：原文片段在本组短窗口中保留了更多限定条件，但两个实验方案都未通过产品验收，不能直接替换 v7。轻量索引在固定查询集上没有增加命中。** 本轮没有改生产代码、没有切换模型、没有升级日用数据库，也没有调用付费模型或提交推送。

原文路线的主要价值是让限定条件不再依赖提炼改写；主要代价是将持久价值筛选、遗忘后的证据边界和性能问题移到了读取阶段。当前证据不足以证明完整系统已经更简单。

## 对照范围与公平性

| 路线 | 本轮实际执行 | 没有执行的部分 |
|---|---|---|
| v7 | 原生产代码；离线重放上一轮 288 个任务、540 个阶段回答；实际调用原 `recall` 和本地检索 | 不重新调用模型，不开启云端向量或精排 |
| 原文片段 | 在同一个任务处理后的隔离库上，检索带角色和来源编号的原文窗口；保留原文字序 | 不自行识别新的聊天遗忘意图；不实现新的后台写入内核 |
| 原文＋轻量索引 | 原文路线＋历史合成提炼回答中的正文作为索引提示；提示不进入输出正文、不能指定项目或全局权限 | 未测新的标签生成提示词或新模型，不把标准答案作为索引 |

288 个宿主回放的最终正文、分类、状态、范围、版本及替代关系全部与旧结果一致。原始模型回答未补字段、未改评分。回放阶段的请求函数直接返回历史字符串，不读取凭据、不连接供应商。

两种原文方案复用原 `MemoryStore.maskSource`、`protections`、`visible` 和证据引用校验。它们不创建第二套遗忘判定词表。当前窗口按单个合成案例的同会话来源组构造；这些案例较短，**不代表已解决真实长会话分块或跨窗口指代**。

全路线统一最多 5 个返回单元、1,500 UTF-8 字节上界，与现有保守 Token 预算函数一致。超预算的原文窗口整块不返回，不截断尾部。原文标记为历史证据，不能被当作确认事实或新指令；但本轮没有调用回答模型，未验证它是否始终遵守该标记。

## 限定条件与召回结果

固定 24 项查询，在 3 个历史模型×2 遍的处理状态上各执行，共每路线 144 次查询、三路线 432 次。限定条件子集为 9 项查询×6 组状态＝54 次；不是 54 个独立新案例。

评分为明确词段及条件同时出现的离线契约检查，不是模型事实准确率或最终回答正确率。检查规则只存在于实验查询文件，不进入生产判断。

| 检查 | v7 | 原文 | 原文＋索引 |
|---|---:|---:|---:|
| 限定条件在同一返回单元中完整出现 | 37/54 | 54/54 | 54/54 |
| 同时保留用户授权范围与工具错误上下文 | 0/6 | 6/6 | 6/6 |
| 已成功执行遗忘的 16 次查询中重新暴露被忘内容 | 0/16 | 0/16 | 0/16 |
| 成功遗忘后的混合消息中，另一事实 B 仍被召回 | 7/8 | 0/8 | 0/8 |
| 项目隔离查询出现跨项目内容 | 0/6 | 0/6 | 0/6 |
| 闲聊／明确不保存的临时指令被召回 | 0/12 | 12/12 | 12/12 |
| 查询其他项目时召回已确认全局偏好 | 6/6 | 0/6 | 0/6 |

不能把上述结果合成一个“总准确率”：原文路线提供历史上下文，v7 提供有效记忆，候选、临时内容的返回语义不同。例如未决选择保留原话，有助于回答“当时是否决定”，但不证明可以当作已确认计划注入。

**具体例子：**

- 端口 8123／8124 与“仅回环地址、不对外网开放”，原文窗口能一起带回；部分 v7 记录拆成两个可分别召回的条目，端口查询漏掉限制。
- “忘掉 SQLite，同时记住 NDJSON”：遗忘成功后，原文窗口的一部分已遮蔽，实验方案为避免留下失去限定的残句而屏蔽整窗，连 NDJSON 也不返回。即使另一事实在下一条消息中，只要仍属于同一实验窗口，也受这个保守策略影响。
- 问“语气”时，原文路线会召回“这次只帮我调整语气，不要保存这个临时请求”。历史证据标签不等于落实了“不保存”的意图。

历史状态中还存在未执行成功的遗忘：Flash 的格式错误在离线回放中原样保留。对应的旧记录没有墓碑，三个读取方案不能凭读取层修正该写入失败。固定查询中 v7 出现 4 次相关内容暴露，原文两组各 8 次，其中新增的 4 次来自混合消息取回整个窗口；不能把这些算成“遗忘已经执行后墓碑失效”。

## 轻量索引有没有收益

最终登记 314 个索引提示实例（包含同一提议在不同来源窗口登记后被引用校验过滤的情况），来源全部是既有合成测试回答。74 次原文＋索引查询中有实际索引词命中，说明不是空索引对照；但固定查询集中，只有索引命中、原文完全不命中的结果为 0，最终返回正文和原文组相同。

`loopback` 查询在三条路线都没有命中；现有输出没有提供该英文别名。另有受控单测使用明确标注的模拟 `loopback` 标签，验证索引可以增加检索入口且不会把标签正文当成记忆输出，但这不是实际模型的标签质量证明。

本轮不能得出“轻量索引永远无效”，只能说：**在这份历史输出和固定查询上，没有证据支持为它增加调用费用与维护负担。** 初次干跑发现阶段记录并非解析后的操作列表，评估器已改为读取原始提炼回答并逐项校验来源，最终结果使用的是实际装载的索引。

## 遗忘保护：机制测试与产品验收分开

原型起始阶段的 20 项机制测试中有 17 项失败；实现保护后，连同新增的分片／来源变化测试，**21/21 通过**。覆盖：

- 跨消息条件与角色顺序；已召回后遗忘；重新创建读取器后的旧来源阻断。
- 只遗忘条件时不能留下无条件主句；相同内容换来源编号和本地近义回放。
- 无精确范围的旧墓碑；跨项目／跨会话拼接拒绝；凭据和已遮蔽控制范围。
- 超预算整窗退出、截断来源、缺失分片、来源变化使旧索引失效。
- 索引只能影响检索，伪造引用不能使用，索引不能提升为全局权限。

随后增加了真正的产品验收，**两种原文路线各有 3 项失败，共 0/6 通过**。这些断言保持失败，没有改成“预期失败即通过”：

| 未通过项 | 观察到的行为 | 为什么不能靠当前机制保证 |
|---|---|---|
| 忘掉同消息 A，保留独立 B | A 不泄漏，但 B 也不返回 | 整窗保守屏蔽没有解决事实依赖与独立边界 |
| 明确不保存的临时指令 | 原文仍可被相关查询命中 | 原文直存没有持久价值／不保存意图判断 |
| 跨语言等义回放 | 忘掉“目录索引存储在 CedarDB”后，新的 `The catalog index is stored in CedarDB.` 仍被返回 | 来源范围只能约束旧来源；当前本地字面和近义匹配不足以确定新表述的事实身份 |

最后一项不能被历史集合上的 0/16 泄漏掩盖，也不能据此声称 v7 的整个新表述保护已经完善。本轮只证明原文新入口会遇到这个问题，未调用模型测试 v7 对该新句子的完整提炼表现。

原型还未接入已确认全局核心记忆和具体事实的重新记住授权；对相似的不同主体可能过度阻断。它不是保持全部原功能的替代版本。

## 复杂度与本地耗时

分支统计与既有工具同口径：`if`、条件表达式、逻辑表达式（含 `??`）、非默认 `case`、`catch` 和循环 AST 节点。

| 统计范围 | 结果 |
|---|---:|
| 冻结的生产 `src/**/*.mjs`＋`dsh/**/*.mjs` | **854 → 854**，源码未改 |
| v7 的 `search`＋`recall` 两个读取方法 | 34 |
| 新原文原型的完整运行模块，含登记、保护、索引与预算 | 41 |
| 新生产协议、服务、依赖 | 0 |

41 不包含复用的存储保护代码；34 同样不包含调用的存储和云端客户端代码。原型还省略了全局核心、云端向量／精排、写入授权、长期整理等能力，因此不能拿“854 对 41”宣称减少了 95% 的复杂度。仓库是在生产代码之外新增实验代码，**没有证明完整替代系统的分支数下降**。

原文读取不调用提炼模型，但本次配对评估共享 v7 的已完成写入决定；“0 次新调用”只代表本轮离线执行，不能当成完整替代方案的实际费用。

规模测量使用同一份合成内存 SQLite 数据，1 个遗忘条目，1 次预热＋5 次测量，交替路线顺序，v7 使用不同消息 ID 防止命中召回快照。以下是中位耗时，不是 P95：

| 记录数 | v7 本地召回 | 原文 | 原文＋索引 |
|---|---:|---:|---:|
| 1,000 | 5.58 ms | 274.26 ms | 328.06 ms |
| 10,000 | 52.61 ms | 5,255.15 ms | 5,900.10 ms |

原型按窗口遍历，每次读取来源并执行保护查询，再计算相关性；这里测到的是这个朴素实现的代价。不能推断原文检索在架构上必然慢，也不能忽略当前实现明显不适合直接上线。没有为了本轮数字继续追加缓存或索引优化。

内存记录是三条路线共存进程的总量：1,000 条约 115.8 MiB RSS，10,000 条约 488.9 MiB RSS；不能当成各路线独立内存占用。完整原始采样见性能 JSON。
