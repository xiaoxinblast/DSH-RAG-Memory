核查与验收日期：2026-11-03。此次只优化读取和临时计算；生产协议仍为 6，数据库仍为 3，近义保护阈值仍为 0.5。未调用付费模型，未读取真实聊天，未更改日用配置、安装或模型，未提交、推送。此次不提供模型准确率结论。

## 结论

本轮通过行为对照和离线回归，可以作为性能整理版本保留。主要收益是减少重复扫描和文本计算，降低候选扫描耗时与进程峰值内存；不是新的记忆决策策略，也不是大幅架构精简。

- 普通新增的一项操作，保护数据收集由 4 次减为 2 次：裁决阶段 1 次，保存前重新收集 1 次。四项新增批次为 16 → 8 次。
- 相同输入的精确/近义分类、旧墓碑、控制范围、遮蔽结果、候选顺序及来源引用，与冻结版本的 1,320 项比较一致。另有重记许可、事务内新增墓碑和对象独立性测试。
- 当前完整套件 155/155；紧邻本轮的冻结核心套件 142/142；更早协议基线 116/116；历史实现 180/180。四组分别运行，不混合为准确率，也不删改旧测试。
- 全生产边界的 AST 分支数 862 → 858，仅减少 4 个。单次稀疏保护查询存在可测退化；下文保留原值。

## 实际改动与职责

生产仅修改 `src/store.mjs`、`src/operations.mjs`、`src/domain.mjs`；另更新现有统一验收入口 `scripts/verify-kernel.mjs`，新增本轮测试、基准脚本和证据文件。

| 原流程 | 现流程 | 保持的约束 |
| --- | --- | --- |
| `factsFor` 为 related、无许可阻断、有许可阻断分别调用保护查询 | 一次 `protections` 收集，由共用 `blockedBy` 分别检查两种许可 | 许可仍绑定事实、版本、范围、新用户来源、正文和操作指纹 |
| 保存时再次查询保护 | 保留 `blocked → protections → blockedBy` 的新查询 | 提交前新增墓碑不能被旧快照绕过；失败回滚且不推进来源检查点 |
| 先载入全部作用域内遗忘记录，再生成两轮过滤数组和 Set | 游标逐行分类为精确或近义结果 | 分类规则和返回行字段不变；最终匹配数组仍按需要保留 |
| 每个来源锚点 × 每条旧记录反复标准化、分词 | 锚点预处理；旧记录逐行预处理，再比较 | 原词项评分公式、Unicode 标准化和 0.5 阈值不变 |
| 按来源顺序反复更新 Map 候选 | 每条记录汇总引用，按第一次命中的锚点排序；同锚点按原记录顺序 | 近义后变精确时仍只保留精确引用，同时保留原发现顺序 |
| 遮蔽时将全部旧墓碑和范围载入 JS 后筛选 | SQLite 按来源 ID 筛选后逐条读取 | 旧墓碑仍整条来源保守遮蔽；精确范围的顺序、裁剪和锚点边界不变 |
| `lexicalScore` 内完成分词和评分 | 保留该入口，调用共用 `scoreTerms`；批量扫描可传已算好的词项和标准化文本 | 召回排序、索引和注入策略不变 |

没有新增中文语义词表，没有新增裁决状态/规则、运行依赖、持久缓存或数据库迁移。`src/policy.mjs` 仍唯一负责最终裁决，执行层没有重解释正文。

## 同条件性能

环境：Windows 10.0.26300、Node v25.9.0、Intel Core i7-13650HX。每组前/后版本在独立新进程，使用相同合成数据和内存 SQLite。记录数指合成遗忘记录总数（含项目、全局、其他项目），不是日用库中的有效记忆数。

两类数据：稀疏组混合哈希、中英日文、全角及短文本；密集组共享大量中文条件表述。每阶段 2 次预热 + 9 次计时，候选输入 4 条合成来源。P95 是 9 次中的最大值，不是生产尾延迟承诺。每次运行还执行一个额外四项新增批次，两个模型阶段完全模拟。结果结构、顺序、来源及批次写入内容的指纹均前后一致。

| 遗忘记录 | 数据 | 候选 P50 ms 前→后 | 候选 P95 ms 前→后 | 进程峰值 RSS MiB 前→后 |
| ---: | --- | ---: | ---: | ---: |
| 1,000 | 稀疏 | 25.44 → 4.63 | 30.99 → 5.83 | 94.82 → 68.03 |
| 1,000 | 密集中文 | 102.56 → 9.45 | 105.28 → 10.09 | 139.67 → 79.74 |
| 10,000 | 稀疏 | 269.23 → 44.03 | 640.75 → 50.87 | 270.62 → 161.91 |
| 10,000 | 密集中文 | 2160.35 → 94.68 | 2459.96 → 101.81 | 318.91 → 252.76 |

RSS 是整个进程峰值，包含 Node、SQLite、数据准备及全部阶段，不能解释为某个函数独占内存。不是堆分配采样，也不是日用部署测量。

| 遗忘记录 | 数据 | 单次保护 P50 ms 前→后 | 四来源遮蔽 P50 ms 前→后 | 四项新增批次单次 ms 前→后 |
| ---: | --- | ---: | ---: | ---: |
| 1,000 | 稀疏 | **4.82 → 5.71（变慢）** | 2.82 → 2.09 | 110.60 → 71.84 |
| 1,000 | 密集中文 | 8.81 → 8.59 | 3.25 → 2.12 | 185.34 → 94.10 |
| 10,000 | 稀疏 | **48.20 → 53.40（变慢）** | 27.36 → 18.97 | 2513.36 → 558.58 |
| 10,000 | 密集中文 | 184.72 → 84.90 | 47.24 → 19.16 | 3447.12 → 1530.17 |

不能把单次批次耗时写成 P50/P95。稀疏单次保护检查在本次测量中约慢 18% / 11%；四项批次因减少重复收集仍下降。当前测量没有独立剖析游标、SQLite JSON 过滤与 GC 各自贡献，不将慢的原因作未经验证的归因。最初优化版本数据也保留在 `.cache/protection-perf/performance-before-alias-fix.json`；以上表格只采用修正对象共享后的最终测量，未选取两轮中的最优值。

原始样本、环境、结果指纹和计数见 [性能 JSON](protection-perf-performance.json)。

## 剩余问题与下一步边界

1. **单次稀疏保护检查退化仍存在。** 若继续做性能工作，先剖析这一条路径，再用相同指纹与范围测试验证；不能为了提速取消保存前重查。
2. **线性扫描和密集候选内存仍存在。** 此次只减少重复计算和无用中间对象，没有引入新索引或筛掉候选。增加候选上限、换近义算法、改短文本判断都会影响行为，需另定策略范围。
3. **记忆质量问题不能由此验收消除。** 原协议下对近义遗忘、限定条件和模型错误的限制全部保留；本次没有真实模型准确率和费用测试，不能宣称这些语义问题已解决。
4. **无日用效果结论。** 尚未安装本版到日用 DSH、运行真实聊天或测日用数据库 I/O；合成内存数据库结果仅作为本轮实现对照。
